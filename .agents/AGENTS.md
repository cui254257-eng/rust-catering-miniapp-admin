# 项目协作规则

## 项目结构

- `apps/admin`：React、TypeScript 管理后台。
- `apps/mini`：uni-app、Vue 3、TypeScript 小程序。
- `apps/api`：Rust、Axum API；业务代码按模块放在 `src/modules/`。
- `packages/contracts`：前后端共享类型。接口数据结构发生变化时，检查并同步相关类型和调用方。

## 协作与修改

1. 代码应简洁、清晰、易懂，优先采用项目已有的实现方式。
2. 修改前先阅读相关代码、调用关系、数据结构和当前工作区状态；只做完成任务所需的最小修改。
3. 有明确复用场景时优先复用现有组件、函数和方法；没有合适抽象时再新增，避免过度抽象。
4. 始终以仓库当前代码为准。保留用户已有修改；不要擅自恢复或更改已存在的接口路径、请求方法、参数、响应结构及其他约定。

## 接口与请求封装

1. 修改接口调用前，先阅读对应端的请求封装：
   - 管理后台：`apps/admin/src/api/client.ts`
   - 小程序：`apps/mini/src/api/request.ts`
2. 当前普通请求会直接返回响应体：后台返回解析后的 JSON，小程序返回 `response.data`。不要重复解包，也不要添加 `res ?? res.data ?? res.data.list` 之类的多层兼容判断；按实际接口结构和类型处理。
3. 当前封装没有 `returnEnvelope` 选项。只有业务确实需要状态码、响应头等完整响应信息时，才按实际需求扩展封装和类型，不要直接使用尚不存在的参数。
4. 新接口需求未指定请求方法时，默认使用 POST；新增前端接口调用时明确写出请求方法。调用已有接口时，必须遵循其当前路由和实现，不得因此改动既有方法。

## 前端与 API 约定

1. Vue 文件中的业务逻辑应添加清晰、简洁的注释，说明关键处理和业务意图；Hooks、composables 等逻辑也应在必要处补充注释。
2. 函数定义前不要添加 `void`。
3. Rust API 按业务模块组织；新增业务优先放在 `apps/api/src/modules/` 对应模块中，按现有模式维护路由、controller、service、repository、DTO 和 entity。跨模块通用代码放在 `common/`。

## 验证限制

1. 进行静态与类型检查
2. 你为了验证新开的端口 代码编写完毕后关闭
